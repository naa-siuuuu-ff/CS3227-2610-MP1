# Reflections on AI-Assisted Software Engineering

## Stage 1: Planning

This is the stage at the start where things can go really wrong. There is a choice to be lazy, and completely outsource the creative process and choice of coming up with an app idea to the LLM, it saves energy, and the potential pain of coming up with an app idea yourself, and finding out later that it has already been made. However, taking this path can cause big problems in the development process, one of them being burnout, due to making a soulless application that you have no connection to.

However, there is another issue, especially for a less experienced developer like me, where given the constraints, I do not know if an idea is feasible. So I decided to come up with an idea myself, and make something that I would want to use or be happy to have made, but let the LLM fine-tune the idea and set constraints to ensure that they are within the project's scope and limitation.

I decided to make a note-taking app, and the LLM helped me land on a markdown editor suitable for JavaFX[cite: 3]. I initially wanted certain functionality like drag-and-drop, but the LLM warned me against that, given the time limitations.

Then I planned the architecture of the application, and cross-checked the one generated by Gemini with Claude, which improved it further. After that, I paused to prompt the LLM to deeply explain to me the chosen architecture, and how it would work when everything is completed, before starting to write code.

I also made a rough plan, which is to make a MVP, then slowly add features and make everything look nicer.

## Stage 2: Making the MVP

Building the Minimum Viable Product was where theory met execution. With the Ports and Adapters structure agreed upon, my priority was establishing an end-to-end walking skeleton before touching advanced styling[cite: 3].

The biggest risk during this stage was allowing the LLM to produce massive monolithic files. When asked broadly to "build the app," LLMs tend to couple JavaFX UI components directly with file input/output and parsing routines. To counter this, I guided the model in strictly decoupled increments:
1. Pure domain entities (`Note`, `FolderNode`)[cite: 1, 3].
2. Storage and renderer port contracts (`NoteRepository`, `MarkdownRenderer`)[cite: 1, 3].
3. Concrete adapters (`FileSystemStorage`, `CommonMarkRenderer`)[cite: 1, 3].
4. Presentation binding through `MainViewModel`[cite: 1, 3].

Whenever the LLM generated sample code importing `javafx.*` into the logic or model packages, I intervened immediately. By enforcing the invariant that core domain packages must remain completely headless, the MVP could be verified in seconds using pure JUnit 5 test stubs[cite: 1, 3].

Once the core data flow worked—persisting a note to disk, debouncing changes, and seeing the CommonMark output render in a basic view—I had a solid baseline[cite: 1, 3].

## Stage 3: Iterating and Refining Features

With the working skeleton in place, I shifted to incremental enhancement:
* **GFM Table and Strikethrough Extensions**: CommonMark out-of-the-box only supports standard CommonMark spec[cite: 1, 3, 4]. I prompted the model to configure GFM extensions and isolate renderer initialization inside `CommonMarkRenderer`[cite: 1, 3, 4].
* **Responsive Layout & CSS Polish**: Migrating raw HTML rendering into an embedded WebKit `WebView` required precise styling[cite: 1, 3]. Here, the LLM was useful for generating clean CSS typography rules for headings, code blocks, and blockquotes, while I ensured the editor input matched the live output pane visually.
* **Document Metrics & Text Statistics**: I wanted live word, character, and line counts[cite: 1]. Rather than letting the UI handle parsing, I instructed the model to create `TextStatistics` as a pure, headless domain record, preserving the testability of our core logic[cite: 1].
* **Text Formatting Shortcuts**: Adding `Ctrl+B`, `Ctrl+I`, and `Ctrl+K` was built by keeping the selection calculation inside `TextFormatter` separate from the JavaFX `TextArea` control[cite: 1, 2].

During this iterative phase, the prompt strategy changed from asking *how* to build something to asking *what edge cases* could break our design. This surfaced issues such as handling duplicate file names (`Title 1.md`) and preventing regex backtracking during tag extraction[cite: 1, 3].

## Stage 4: Testing and Verification

AI-assisted development can give a false sense of security; code that looks elegant can fail under real operating conditions. Testing was where I held the LLM to strict accountability.

Instead of writing tests after the fact, I prompted the LLM to provide edge-case test suites for headless execution:
* Handling special characters and collisions during file persistence (`FileSystemStorage`)[cite: 1, 3].
* Tag extraction with irregular spacing, punctuation, and mixed casing (`#tag_1`, `#123`, `#tag-name`)[cite: 3].
* Search queries alternating between raw keywords and explicit `#` tag filters[cite: 1, 3].

Because the architecture prevented UI coupling, the entire domain test suite executed via `mvn test` in under one second without headless display virtualizers like Xvfb[cite: 1, 3]. Testing peer workflows manually alongside automated tests confirmed that auto-saving, conflict resolution, and Markdown rendering matched the documented specifications[cite: 1, 2, 3].

## Prompt Deep Dives: 3 Key Prompts & Analysis

### Deep Dive 1: Architectural Boundary Enforcement & Anti-Coupling
* **Prompt**:
  > *"I want to set up our core business logic and domain classes (`Note`, `SearchEngine`, `NotebookManager`)[cite: 3]. Before writing any code, remember our architectural invariant: under NO circumstances may any class in `com.notebook.model` or `com.notebook.logic` import anything from `javafx.*`[cite: 1, 3]. Write `Note.java` as an immutable record or class with defensive copies for tags, and provide the port interface `NoteRepository`[cite: 1, 3]. Explain how you ensure zero framework leakage."*
* **Why it was used**: LLMs default to convenient UI bindings (e.g., `StringProperty`, `ObservableList`) when creating models for JavaFX applications. Left unchecked, this ruins headless testability[cite: 1, 3].
* **Outcome & Analysis**: Explicit negative prompting ("under NO circumstances...") combined with architectural context forced the LLM to produce pure Java domain structures[cite: 1, 3]. It utilized standard collections (`Set<String>`, `List<Note>`) and immutable defensive copies[cite: 1, 3]. This ensured `mvn test` ran quickly without initializing the JavaFX graphics toolkit[cite: 3].

---

### Deep Dive 2: Debugging the WebView Template String Formatting Bug
* **Prompt**:
  > *"When rendering HTML inside our `PreviewPane` via `WebView`, calling `String.format(template, markdownBody)` throws an `UnknownFormatConversionException` whenever the CSS contains percentage signs (e.g., `width: 100%`)[cite: 1, 3]. Refactor the template replacement mechanism without breaking the HTML structure or requiring complex regex."*
* **Why it was used**: The application crashed when loading certain styled preview pages. The LLM initially favored `String.format()` with an HTML wrapper template, but CSS style declarations like `max-width: 100%` collided with Java's format specifiers.
* **Outcome & Analysis**: The model quickly diagnosed that `%` is treated as a format specifier by `Formatter`. It refactored the pipeline to use deterministic placeholder substitution: `template.replace("{{BODY}}", markdownBody)`[cite: 1, 3]. This fixed the crash, simplified the rendering adapter, and avoided runtime string formatting exceptions[cite: 1, 3].

---

### Deep Dive 3: Decoupled Editor Formatting & Selection Logic
* **Prompt**:
  > *"We need keyboard formatting shortcuts (`Ctrl+B` for bold `**`, `Ctrl+I` for italic `*`, `Ctrl+K` for code `` ` ``)[cite: 2]. However, I do not want the string manipulation and cursor index calculation logic inside the JavaFX `MainWindow` controller[cite: 1]. Write a standalone, pure Java class `TextFormatter` that takes the full text, selection start, selection end, and the wrap token[cite: 1]. It must return a result object containing the modified full text, new selection start, and new selection end[cite: 1]. Cover cases where text is highlighted vs where the caret is collapsed."*
* **Why it was used**: Controller classes easily turn into "God classes" if text manipulation, event handling, and layout management are combined. I used the LLM to offload the string-slicing logic into a pure domain utility[cite: 1].
* **Outcome & Analysis**: The LLM produced `TextFormatter` and its accompanying record `FormatResult`[cite: 1]. If text was selected, it wrapped the boundaries (`**selection**`)[cite: 2]. If no text was selected, it inserted the double tokens (`****`) and returned the middle caret index[cite: 2]. Crucially, because it took pure strings and primitive ints, I was able to write unit tests for shortcut actions without launching JavaFX UI components[cite: 1, 3].

## Takeaways on AI-Assisted Software Engineering

Working with LLMs throughout this project reshaped my understanding of software engineering:
* **The Developer Remains the Architect**: An LLM can generate code instantly, but it cannot evaluate trade-offs regarding maintainability, dead ends, or personal project scope. The human must define the boundaries, review every file, and steer the design[cite: 3].
* **Modularity Protects Against Hallucination**: Strict architectural separation (such as Hexagonal Architecture) compartmentalizes LLM errors[cite: 1, 3]. When logic is decoupled from UI, bugs are isolated to single adapters rather than cascading across the application[cite: 1, 3].
* **Verification Over Generation**: The value of prompting lies not in generating large blocks of code, but in generating precise, verifiable modules accompanied by test assertions[cite: 1, 3]. The habit of cross-checking designs across models and enforcing strict headless testing turned the LLM into an effective programming collaborator[cite: 1, 3].

## Chat Hygiene & Context Window Management

A crucial practical lesson I learned was managing the LLM's context window. Allowing chat threads to run indefinitely introduces subtle degradation:
* **Context Bloat & Token Degradation**: As conversations grew excessively long, the model began conflating previous, discarded iterations with current implementations. It would reintroduce deprecated patterns or hallucinate methods from earlier drafts.
* **Periodic Summarization and Fresh Chats**: To counter this, I adopted a strict chat hygiene workflow: periodically prompting the model to produce a concise technical summary of the current working state, saving that snapshot, and starting a fresh chat session. Providing this clean summary as the opening prompt in a new window restored the model’s focus and eliminated lingering context pollution.
* **Value of Direct, Low-Overhead Reasoning in Mature Chats**: I observed that when chats did become longer, enabling extensive reasoning or "overthinking" actually worsened results. The model tended to overanalyze superseded context and overcomplicate simple changes. Giving shorter, direct, and more matter-of-fact instructions with lower thinking overhead prevented context mixing and produced cleaner, more deterministic code.
