# Reflections on AI-Assisted Software Engineering

## Stage 1: Planning

This early stage is where a project can quietly go wrong before a single line of code is written. It's tempting to hand the entire creative decision — the app idea itself — over to the LLM: it's less effortful, and it sidesteps the discomfort of proposing something that might turn out to already exist. But taking that shortcut carries a real cost. Building something you have no personal stake in is a fast route to burnout, especially over a project this compressed.

There's a second, more personal issue too. As a less experienced developer, I genuinely didn't know which ideas were realistic within the time and skill constraints I had. So I split the decision in two: I came up with an idea I actually wanted to build and would be glad to have made, and let the LLM act as a feasibility check — fine-tuning scope and flagging constraints rather than inventing the concept from scratch.

That's how I landed on a markdown editor for JavaFX. I'd originally wanted drag-and-drop note organization, but the LLM pushed back on that given the time available, and in hindsight that was the right call — it would have eaten days I didn't have.

From there I planned the application architecture, and deliberately cross-checked a version generated by Gemini against one from Claude, using the disagreement between them to sharpen the final design. Before writing any code, I paused and asked the LLM to walk me through the chosen architecture end-to-end — what each piece was for and how it would all fit together once finished — rather than diving into implementation on faith.

I also sketched a rough build order at this stage: get a minimum viable product working first, then layer on features and polish incrementally rather than trying to build everything at once.

## Stage 2: Making the MVP

This is where architecture met implementation. With the ports-and-adapters structure agreed on, the priority was an end-to-end walking skeleton — something that worked, thinly, across every layer — before any styling or polish.

The biggest risk at this stage was the LLM's tendency to produce large, coupled files. Asked broadly to "build the app," it defaulted to wiring JavaFX components directly to file I/O and parsing logic in the same class. To prevent that, I broke the work into strictly ordered, decoupled increments and reviewed each before moving to the next:

1. Pure domain entities (`Note`, `FolderNode`).
2. Port contracts (`NoteRepository`, `MarkdownRenderer`).
3. Concrete adapters (`FileSystemStorage`, `CommonMarkRenderer`).
4. Presentation binding through `MainViewModel`.

Any time the model reached for `javafx.*` inside the model or logic packages — even in a "just for now" way — I stopped and corrected it immediately. Holding that line meant the MVP could be verified in seconds using plain JUnit 5 stubs, with no display server or UI toolkit involved.

Once a note could be created, persisted to disk, edited with a debounce, and rendered live through CommonMark, I had a genuine baseline — not a mockup, an actual working slice of the real app. I also used this stage to pressure-test the build plan itself: rather than assume there was comfortable time for a slow feature rollout, I had the LLM help lay out a day-by-day plan — headless core first, UI wiring second, one differentiating feature third, documentation and buffer last — which turned out to matter more than expected once I realized how little time was actually left before the deadline.

## Stage 3: Iterating and Refining Features

With the skeleton working, the focus shifted to incremental enhancement, each addition scoped to fit inside the existing architecture rather than reshaping it:

- **GFM table and strikethrough support**: standard CommonMark alone doesn't cover GitHub-flavoured tables or strikethrough, so I had the model configure the relevant extensions and keep their initialization isolated inside `CommonMarkRenderer`, rather than leaking configuration details into the rest of the app.
- **Responsive layout and CSS polish**: moving rendered HTML into an embedded WebKit `WebView` needed careful styling to look intentional rather than like unstyled browser output. The LLM was genuinely useful here for generating clean typography rules for headings, code blocks, and blockquotes, while I made sure the editor and the live preview stayed visually consistent with each other.
- **Document metrics**: I wanted live word, character, and line counts. Rather than letting the UI parse the text directly, I had the model implement `TextStatistics` as a pure, headless domain type, so the count logic stayed just as testable as everything else in the core.
- **Formatting shortcuts**: `Ctrl+B`, `Ctrl+I`, and `Ctrl+K` were implemented by keeping the selection math inside a standalone `TextFormatter` class, separate from the `TextArea` control itself.
- **Small, deliberately low-risk additions near the deadline**: word/character counts, a force-save shortcut, and a light/dark preview toggle were chosen specifically because each one touched only a single layer and carried close to zero risk of breaking what already worked — a very different selection process from the earlier, more exploratory feature choices.

During this phase the prompting shifted in character — from asking *how* to build something, to asking *what could break it*. That shift surfaced real issues before they became bugs: duplicate file names needed to become `Title 1.md` instead of overwriting, and the tag-extraction regex needed guarding against pathological backtracking on malformed input.

## Stage 4: Testing and Verification

AI-assisted development can create a false sense of security — code that reads cleanly can still fail under real conditions. Testing was where I held the model to the highest standard of accountability, treating its suggestions as claims to be verified rather than facts.

Rather than writing tests after the fact, I asked the LLM to propose edge-case test suites upfront, for headless execution:

- Special characters and filename collisions during persistence (`FileSystemStorage`).
- Tag extraction under irregular spacing, punctuation, and mixed casing (`#tag_1`, `#123`, `#tag-name`).
- Search queries that mix plain keywords with explicit `#tag` filters.

Because the architecture kept the UI decoupled from the core, the entire domain test suite ran through `mvn test` in under a second, with no display virtualization needed for CI. I supplemented that automated coverage with manual walkthroughs of real usage — creating, editing, and searching notes by hand — to confirm that autosave, conflict handling, and rendering all matched what the documentation claimed, rather than trusting the tests alone to catch everything a real user would hit.

## Prompt Deep Dives: Key Prompts & Analysis

### Deep Dive 1: Architectural Boundary Enforcement & Anti-Coupling

**Prompt:**
> "I want to set up our core business logic and domain classes (`Note`, `SearchEngine`, `NotebookManager`). Before writing any code, remember our architectural invariant: under NO circumstances may any class in `com.notebook.model` or `com.notebook.logic` import anything from `javafx.*`. Write `Note.java` as an immutable record or class with defensive copies for tags, and provide the port interface `NoteRepository`. Explain how you ensure zero framework leakage."

**Why it was used:** LLMs default to convenient UI bindings (`StringProperty`, `ObservableList`) when generating models for a JavaFX app. Left unchecked, that quietly destroys headless testability.

**Outcome & analysis:** Explicit negative framing — "under NO circumstances" — combined with the architectural context forced genuinely pure Java domain structures: standard collections (`Set<String>`, `List<Note>`), immutable types, defensive copies on the mutable-looking fields. The payoff was concrete, not theoretical: `mvn test` ran without ever touching the JavaFX graphics toolkit.

---

### Deep Dive 2: Debugging the WebView Template Formatting Bug

**Prompt:**
> "When rendering HTML inside our `PreviewPane` via `WebView`, calling `String.format(template, markdownBody)` throws an `UnknownFormatConversionException` whenever the CSS contains percentage signs (e.g. `width: 100%`). Refactor the template replacement mechanism without breaking the HTML structure or requiring complex regex."

**Why it was used:** The app crashed on certain styled preview pages. The original template approach used `String.format()` with an HTML wrapper, and CSS declarations like `max-width: 100%` collided with Java's format-specifier syntax.

**Outcome & analysis:** The model correctly diagnosed that `%` is parsed as a format conversion by `Formatter`, and switched the pipeline to deterministic token substitution — `template.replace("{{BODY}}", markdownBody)` — instead of a patch aimed only at the CSS rule that happened to trigger the crash. That fixed the bug and removed an entire category of runtime formatting exceptions at once.

---

### Deep Dive 3: Decoupled Editor Formatting & Selection Logic

**Prompt:**
> "We need keyboard formatting shortcuts (`Ctrl+B` for bold `**`, `Ctrl+I` for italic `*`, `Ctrl+K` for code `` ` ``). I don't want the string manipulation and cursor-index calculation living inside the JavaFX `MainWindow` controller. Write a standalone, pure Java class `TextFormatter` that takes the full text, selection start, selection end, and the wrap token. It must return a result object containing the modified full text and the new selection start and end. Cover the cases where text is highlighted and where the caret is collapsed."

**Why it was used:** Controllers turn into God classes fast when text manipulation, event handling, and layout all live in one place. Offloading the string-slicing logic to a pure domain utility kept `MainWindow` focused on wiring, not computation.

**Outcome & analysis:** The model produced `TextFormatter` and an accompanying `FormatResult` record. Selected text gets wrapped at its boundaries (`**selection**`); a collapsed caret gets the paired tokens inserted with the cursor left in the middle. Because the whole thing operates on plain strings and primitive ints, I could unit-test every shortcut without ever launching a JavaFX component.

### Deep Dive 4: Re-planning Under a Compressed Deadline

**Prompt (paraphrased from an ongoing planning conversation):** After discussing the architecture and a two-week build plan in detail, I flagged the actual submission deadline and asked the assistant to re-derive the plan from scratch: what should change if the real time remaining was closer to fifteen hours than two weeks, given everything already built.

**Why it was used:** Plans made early in a project tend to anchor on the assumptions available at the time. I wanted an explicit check on whether the original MVP-then-features roadmap still held once the actual time budget was known, rather than continuing on inertia.

**Outcome & analysis:** The response wasn't more code — it was a re-prioritized triage list, ranked by risk and grading weight: fix a visible bug already showing in the running app before adding anything new, tag a working commit as insurance, then only add features that were small, single-layer, and reversible, explicitly deferring anything that touched the domain model or added new UI surface. It also flagged that documentation and reflections carry more combined grading weight than any single new feature and take no coding time at all, which reordered my remaining hours more than any code change did. This was the clearest example in the whole project of a case where the most valuable thing the LLM produced wasn't code, but a corrected plan.

## Takeaways on AI-Assisted Software Engineering

Working with LLMs throughout this project reshaped how I think about software engineering:

- **The developer remains the architect.** An LLM can generate code instantly, but it cannot weigh trade-offs about maintainability, project scope, or what's actually worth building given the time available. A human has to set the boundaries, review every file, and own the design decisions.
- **Modularity limits the blast radius of hallucination.** Strict architectural separation — hexagonal architecture in this case — compartmentalizes LLM errors. When logic is decoupled from UI, a bad suggestion breaks one adapter, not the whole application.
- **Verification matters more than generation.** The real value of prompting wasn't in producing large blocks of code — it was in producing small, verifiable modules paired with test assertions. Cross-checking designs across models and enforcing headless testing is what turned the LLM from a code generator into an actual collaborator.
- **The most valuable prompt isn't always about code.** The single highest-leverage exchange in this project was re-deriving the build plan once I realized how little time was actually left. No code came out of it, but it changed almost everything I did in the hours that followed. Knowing when to stop and ask "is the plan still right?" turned out to be at least as important as any individual implementation prompt.

## Chat Hygiene & Context Window Management

A practical lesson that had nothing to do with code: managing the LLM's context window mattered more than I expected. Letting a single chat thread run indefinitely introduces a subtle kind of decay.

- **Context bloat and degradation**: as a conversation grew very long, the model started conflating earlier, discarded iterations with the current implementation — reintroducing patterns I'd already moved away from, or referencing methods that only existed in an earlier draft.
- **Periodic summarization and fresh starts**: to counter this, I adopted a habit of periodically asking the model to produce a concise technical snapshot of the current working state, saving it, and opening a fresh chat with that snapshot as the first message. It reliably restored focus and cleared out lingering confusion from superseded context.
- **Less reasoning, not more, in mature chats**: counterintuitively, turning on extended or "extra thinking" reasoning modes in long-running chats made things worse, not better — the model tended to overanalyze context that no longer applied and overcomplicate what should have been simple edits. Short, direct, matter-of-fact instructions with lower reasoning overhead consistently produced cleaner, more deterministic code once a chat had accumulated a lot of history.
